## DEP-VULN-001

**Dependency with a known vulnerability**

A package version in the lockfile matches an advisory in the OSV database (GitHub Advisory Database, malicious package reports, ...).

- Category: dependency-vulnerability
- Default severity: HIGH
- Default confidence: HIGH

**Remediation:** Upgrade to a fixed version (see the finding), or remove the dependency. Re-run `npm audit fix` or update the lockfile and review the changes.

**Limitations:** Matches the exact versions in the root package-lock.json against advisory data; it cannot tell whether your code calls the vulnerable function. Severity comes from the advisory (or CVSS v3 vector) and defaults to MEDIUM when absent. yarn.lock, pnpm-lock.yaml and nested lockfiles are not analysed yet.

References:

- https://osv.dev/
- https://cwe.mitre.org/data/definitions/1395.html

## JS-CFG-001

**Insecure http:// endpoint**

A hardcoded http:// URL sends traffic unencrypted and allows interception or tampering on the network path.

- Category: configuration
- Default severity: LOW
- Default confidence: MEDIUM

**Remediation:** Use https:// (or a protocol-relative configuration value that is https in production).

**Limitations:** Loopback, .local/.test hosts and well-known namespace URLs are ignored. Cannot tell whether the URL is only used in development.

References:

- https://cwe.mitre.org/data/definitions/319.html

## JS-CFG-002

**Secret-looking value in a public frontend environment variable**

Variables with prefixes such as VITE_, REACT_APP_ or NEXT_PUBLIC_ are embedded into the browser bundle at build time. Anything stored there is visible to every visitor.

- Category: configuration
- Default severity: MEDIUM
- Default confidence: MEDIUM

**Remediation:** Keep secrets on the server and expose only a narrowly scoped endpoint to the frontend.

**Limitations:** Judges by the variable name. Public identifiers such as map or analytics keys are legitimately exposed; names containing only KEY are reported as LOW.

References:

- https://vite.dev/guide/env-and-mode#env-files
- https://cwe.mitre.org/data/definitions/540.html

## JS-EXEC-001

**Dynamic code execution (eval / Function constructor)**

eval() and the Function constructor compile strings into code. With non-constant input this allows arbitrary code execution and defeats Content-Security-Policy hardening.

- Category: code-execution
- Default severity: HIGH
- Default confidence: MEDIUM

**Remediation:** Remove dynamic evaluation. Use JSON.parse for data, lookup tables for dispatch, or a real parser.

**Limitations:** Reports the API usage, not a proven exploit. A call with only constant strings is reported as LOW. Aliased calls such as `const e = eval` are not followed.

References:

- https://developer.mozilla.org/docs/Web/JavaScript/Reference/Global_Objects/eval#never_use_direct_eval!
- https://cwe.mitre.org/data/definitions/95.html

## JS-EXEC-002

**String passed to setTimeout/setInterval**

Passing a string instead of a function to a timer makes the browser evaluate it like eval(). It breaks strict Content-Security-Policy and is a code-injection sink.

- Category: code-execution
- Default severity: MEDIUM
- Default confidence: HIGH

**Remediation:** Pass a function: setTimeout(() => doWork(value), delay).

**Limitations:** Only detects string literals, templates and string concatenations; strings held in variables are not seen.

References:

- https://developer.mozilla.org/docs/Web/API/setTimeout#the_this_problem
- https://cwe.mitre.org/data/definitions/95.html

## JS-MSG-001

**postMessage with wildcard target origin**

window.postMessage(data, "*") delivers the message to whatever origin currently occupies the target window. Sensitive data can be received by an attacker page.

- Category: postmessage
- Default severity: MEDIUM
- Default confidence: MEDIUM

**Remediation:** Pass the exact expected origin as the second argument.

**Limitations:** Severity depends on how sensitive the posted data is, which a static scan cannot judge.

References:

- https://developer.mozilla.org/docs/Web/API/Window/postMessage#security_concerns
- https://cwe.mitre.org/data/definitions/345.html

## JS-MSG-002

**message event handler without origin check**

A window 'message' listener receives messages from any origin. Without verifying event.origin, any page that can obtain a reference to this window can send it data.

- Category: postmessage
- Default severity: MEDIUM
- Default confidence: MEDIUM

**Remediation:** Compare event.origin against an allow-list before using event.data.

**Limitations:** Handlers that cannot be resolved inside the same file (imported functions, inline references to other modules) are not analysed. Origin checks performed by a helper function are not recognised.

References:

- https://developer.mozilla.org/docs/Web/API/Window/postMessage#security_concerns
- https://cwe.mitre.org/data/definitions/346.html

## JS-STORE-001

**Sensitive-looking data in web storage or cookies**

Tokens, passwords and similar values stored in localStorage, sessionStorage or script-set cookies are readable by any script on the page, so an XSS flaw exposes them.

- Category: storage
- Default severity: LOW
- Default confidence: LOW

**Remediation:** Prefer HttpOnly, Secure, SameSite cookies set by the server for session credentials. Never hardcode credentials.

**Limitations:** Decides from the key name only. Storing a token in localStorage is a trade-off, not always a vulnerability, so dynamic values are reported with LOW confidence.

References:

- https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html#local-storage
- https://cwe.mitre.org/data/definitions/922.html

## JS-TAINT-001

**DOM-based XSS: untrusted data reaches an HTML sink**

Data from an attacker-controllable source (URL, window.name, postMessage, input field) flows into an HTML-parsing sink such as innerHTML, document.write or dangerouslySetInnerHTML without a sanitizer for HTML.

- Category: xss
- Default severity: HIGH
- Default confidence: HIGH

**Remediation:** Do not insert untrusted data as HTML. Use textContent / React text nodes, or sanitize with DOMPurify immediately before the sink.

**Limitations:** Intra-procedural: only flows inside one file are followed, through assignments, destructuring, string operations and a small set of known sources/sanitizers. Values returned from functions, passed as arguments, fetched over the network or guarded by custom validation are not tracked, so a missing finding does not prove safety.

References:

- https://cheatsheetseries.owasp.org/cheatsheets/DOM_based_XSS_Prevention_Cheat_Sheet.html
- https://cwe.mitre.org/data/definitions/79.html

## JS-TAINT-002

**Code injection: untrusted data reaches a code execution sink**

Data from an attacker-controllable source flows into eval(), the Function constructor or a string-based timer, which allows arbitrary script execution.

- Category: code-execution
- Default severity: CRITICAL
- Default confidence: HIGH

**Remediation:** Never evaluate untrusted strings. Parse data with JSON.parse and dispatch with explicit lookup tables.

**Limitations:** Intra-procedural: only flows inside one file are followed, through assignments, destructuring, string operations and a small set of known sources/sanitizers. Values returned from functions, passed as arguments, fetched over the network or guarded by custom validation are not tracked, so a missing finding does not prove safety.

References:

- https://cwe.mitre.org/data/definitions/95.html

## JS-TAINT-003

**Untrusted data reaches a navigation or link sink**

Data from an attacker-controllable source decides a link or navigation target. This enables open redirects and javascript: URL script execution.

- Category: url
- Default severity: MEDIUM
- Default confidence: HIGH

**Remediation:** Validate the target against an allow-list of paths or origins, and reject any scheme other than http(s), before navigating.

**Limitations:** Intra-procedural: only flows inside one file are followed, through assignments, destructuring, string operations and a small set of known sources/sanitizers. Values returned from functions, passed as arguments, fetched over the network or guarded by custom validation are not tracked, so a missing finding does not prove safety. Allow-list checks written as conditions around the sink are not recognised and can cause false positives.

References:

- https://cheatsheetseries.owasp.org/cheatsheets/Unvalidated_Redirects_and_Forwards_Cheat_Sheet.html
- https://cwe.mitre.org/data/definitions/601.html

## JS-URL-001

**javascript: URL**

A javascript: URL executes code when followed. It is used in links and navigation targets and is blocked by a strict Content-Security-Policy.

- Category: url
- Default severity: MEDIUM
- Default confidence: HIGH

**Remediation:** Use an event handler or a button element instead of a javascript: URL.

**Limitations:** Only constant javascript: URLs in link attributes, href/src assignments and navigation calls are reported. Dynamic URLs are covered by JS-TAINT-003.

References:

- https://cwe.mitre.org/data/definitions/79.html
- https://developer.mozilla.org/docs/Web/URI/Reference/Schemes/javascript

## JS-XSS-001

**Dynamic value assigned to innerHTML/outerHTML**

A non-constant value is assigned to innerHTML or outerHTML. If any part of it is attacker-controlled the page is vulnerable to cross-site scripting. This rule only notes the risky API; JS-TAINT-001 reports flows from a proven untrusted source.

- Category: xss
- Default severity: MEDIUM
- Default confidence: LOW

**Remediation:** Use textContent for text, build nodes with createElement, or sanitize the markup with a maintained sanitizer such as DOMPurify before assigning it.

**Limitations:** Does not know where the value comes from, so the confidence is LOW. Constant strings and values passed through well-known sanitizers are ignored; custom sanitizers are not recognised.

References:

- https://cheatsheetseries.owasp.org/cheatsheets/DOM_based_XSS_Prevention_Cheat_Sheet.html
- https://cwe.mitre.org/data/definitions/79.html

## JS-XSS-002

**React dangerouslySetInnerHTML with dynamic markup**

dangerouslySetInnerHTML bypasses React's escaping. Dynamic markup that contains attacker-controlled content leads to cross-site scripting.

- Category: xss
- Default severity: MEDIUM
- Default confidence: LOW

**Remediation:** Render the content as React elements, or sanitize it with DOMPurify before passing it in.

**Limitations:** Cannot tell whether the markup is trusted. Constant strings and DOMPurify/sanitize-html calls are ignored; a variable that was sanitized elsewhere is still reported.

References:

- https://react.dev/reference/react-dom/components/common#dangerously-setting-the-inner-html
- https://cwe.mitre.org/data/definitions/79.html

## JS-XSS-003

**Dynamic HTML passed to insertAdjacentHTML or document.write**

insertAdjacentHTML, document.write and document.writeln parse their argument as HTML. A dynamic argument can introduce attacker-controlled markup.

- Category: xss
- Default severity: MEDIUM
- Default confidence: LOW

**Remediation:** Insert text with textContent/insertAdjacentText, or sanitize the markup first.

**Limitations:** Does not know the origin of the argument. Constant strings and recognised sanitizer calls are ignored.

References:

- https://cheatsheetseries.owasp.org/cheatsheets/DOM_based_XSS_Prevention_Cheat_Sheet.html
- https://cwe.mitre.org/data/definitions/79.html

## SEC-AWS-001

**AWS access key ID**

An AWS access key identifier is present in the source.

- Category: secrets
- Default severity: HIGH
- Default confidence: HIGH

**Remediation:** Revoke and rotate the credential, remove it from the code and its git history, and load it from a secret manager or environment at runtime.

**Limitations:** Detected by pattern. The value may be a revoked, test or example credential; the scanner cannot check whether it is still valid.
